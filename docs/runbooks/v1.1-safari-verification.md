# v1.1 Installed Safari Verification

Executed on 2026-10-16 in installed Safari 27.0.1, macOS platform build 26A434,
using SafariDriver/W3C WebDriver, the running local Compose stack and real
synthetic PDFs. This was not a Playwright WebKit browser or a mobile simulator.
The user enabled remote automation after the first session attempt was refused.

## Automation Limits

Pietro subsequently checked the review workspace manually at 200% page zoom
in normal Safari and reported that it looked correct. This records a
user-reported visual pass, not automated measurement or a complete keyboard
check. Pietro then checked 300%, the highest zoom offered by his Safari UI,
and reported no visual issues. A Safari 400% result is unavailable, not a pass;
the earlier Chromium 400% verification retains its own browser scope.
Pietro subsequently enabled Safari's option to highlight every webpage item
with Tab, restored 100% zoom and reported that the guided Tab/Shift-Tab check
worked. This is a user-reported pass for the tested review controls, not a
VoiceOver result or a verified traversal of native PDF controls.

Command-plus/Command-zero actions did not produce a confirmed viewport or
device-pixel-ratio change, so no real page-zoom pass was recorded. macOS reported
that assistive UI automation was unavailable. Later attempts to reach the native
PDF zoom toolbar did not complete; a click probe showed no delivered DOM click
in that session state. This is insufficient to attribute a product bug or a
successful native-zoom interaction. Do not infer zoom coverage from CSS scaling
or screenshot size.

The first verification script had a quoting error in an iframe selector. It was
corrected locally and resumed using the already uploaded documents. Narrow-view
screenshots were then repeated with explicit pressed/visible/hidden-state waits.
No application implementation was changed in response to these harness issues.
