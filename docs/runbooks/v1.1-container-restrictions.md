# v1.1 Application Container Restrictions

Implemented and verified on 2026-10-16 for the local Compose demo. The common
`x-application-security` policy applies to API, console, dispatcher, migrations
and worker. It drops all Linux capabilities and enables no-new-privileges,
including for children such as the OCR subprocess. Existing non-root image
users remain in effect.

## Local Budgets

| Service | CPU quota | RAM limit | RAM plus swap limit | PID limit |
| --- | --- | --- | --- | --- |
| API | 1 CPU | 512 MiB | 512 MiB | 128 |
| Console | 0.5 CPU | 128 MiB | 128 MiB | 64 |
| Dispatcher | 0.5 CPU | 256 MiB | 256 MiB | 64 |
| Migrations | 1 CPU | 512 MiB | 512 MiB | 64 |
| Worker | 2 CPUs | 1 GiB | 1 GiB | 256 |

These are initial local-demo budgets, not load-tested capacity estimates. The
worker receives more memory and CPU for native PDF/OCR work. PID budgets also
cover threads. The Compose service-level settings apply to ordinary local
containers; they do not depend on Swarm deployment. Setting `memswap_limit`
equal to `mem_limit` disables additional swap for these containers. See the
[Compose service reference](https://docs.docker.com/reference/compose-file/services/).

CPU limits throttle work; they are not per-document timeouts. A memory limit
can cause process termination, and a PID limit can prevent process/thread
creation. A killed worker cannot reliably persist its own failure; Temporal
timeouts and retries still determine workflow recovery. Worker and dispatcher
retain their existing `unless-stopped` restart policy. Automatic recovery from
actual OOM or PID exhaustion was not tested.

## Real Runtime Verification

The shared backend image was rebuilt from the current source, including the
OCR pixel-limit change. Application containers were recreated against the
existing PostgreSQL, Temporal and blob volumes. Infrastructure services and
their budgets were not changed. All five application services were inspected:

- Docker HostConfig contains the expected CPU, memory, swap and PID limits,
  `CapDrop=[ALL]`, no-new-privileges and no privileged mode.
- Every running application process reports `NoNewPrivs=1`, with zero effective
  and bounding capability masks. Users are 10001 for backend processes and
  101 for the console.
- Runtime cgroups confirm CPU quotas, memory/PID ceilings and zero swap budget.
- The restricted migration container exits successfully. It ran again during
  the controlled worker restart without a schema/startup error.
- The API and console are healthy. Real uploads through the console proxy
  reach review for digital and scanned invoices, and unsupported status for
  the equipment report. OCR evidence identifies Tesseract.
- A synthetic oversized blank page fails at `OCR_TEXT_EXTRACTION` after retries,
  with its failure stored and available through the API. A subsequent ordinary
  scanned invoice completes OCR successfully in the same worker.
- With the worker stopped, another scanned upload remains queued. Restarting
  the restricted worker completes its OCR and sends it to review.
- Authenticated source retrieval returns the exact uploaded PDF bytes,
  confirming the stored-blob round trip on the existing named volume.
- A separate temporary named volume supports create/write/read/delete as UID
  10001 with no-new-privileges. Only that temporary probe volume was removed.

Observed peaks during this small sequential smoke run:

| Service | Cgroup memory peak | Cgroup PID peak | OOM/OOM-kill events |
| --- | --- | --- | --- |
| API | 121.4 MiB | 12 | 0 / 0 |
| Console | 18.4 MiB | 18 | 0 / 0 |
| Dispatcher | 70.1 MiB | 10 | 0 / 0 |
| Worker | 188.0 MiB | 16 | 0 / 0 |

These peaks are not representative of concurrent uploads, maximum-size PDFs,
all OCR languages or other architectures. The migration container was already
exited when runtime peaks were collected. Existing data volumes were preserved;
verification added only synthetic documents.

## Limits and Follow-up

The policy covers application containers in this Compose file. PostgreSQL,
Temporal and optional observability services need their own sizing and review
for any deployment design. Host-run processes do not inherit Compose limits.
The root filesystem remains writable; a read-only design requires explicit
temporary-file and NGINX-directory handling. PDF parsing is not isolated in a
disposable per-document process, and aggregate container budgets do not provide
fairness between documents.

No package CVE was fixed or suppressed by these settings. The previous
[image scan and triage](v1.1-image-cve-triage.md) refer to the earlier image;
the newly rebuilt image was not rescanned in this checkpoint. Version metadata
remains in development, and v1.1 residual-risk acceptance is still pending.

Local evidence and repeatable workflow script are in the analysis directory:
`verify-container-hardening.py`, `container-hardening-results.json` and
`fresh-volume-hardening-results.json`. The workflow script records image IDs,
runtime limits and synthetic document identifiers, without credentials or
document contents. Build/start/workflow logs were retained locally.
