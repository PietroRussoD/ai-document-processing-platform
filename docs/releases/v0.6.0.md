# v0.6.0 - Controlled Reprocessing

## Scope

`v0.6.0` adds a controlled recovery path for a completed document. Instead of
restarting or overwriting an old processing run, an authenticated operator
creates a replacement run with explicit immutable lineage and a durable audit
record. The operator console exposes that workflow without displaying document
text, storage paths or credentials.

## Included

- `POST /api/v1/documents/{document_id}/reprocessing-requests`, protected by
  the existing local development bearer-token fixture and requiring a bounded
  idempotency key and reason;
- a replacement `QUEUED` processing run with `previous_run_id` pointing to the
  terminal source run;
- immutable `reprocessing_operations` audit records containing bounded operator
  identity, reason, request time, source run, replacement run and request
  fingerprint;
- idempotent replay for an equivalent request and `409` conflict responses for
  changed payloads or a non-terminal source run;
- PostgreSQL constraints that permit at most one active run per document, even
  when multiple API instances receive competing requests;
- Temporal handoff for the replacement run, preserving the original blob and
  producing independent extraction and validation evidence;
- status and generated OpenAPI contracts exposing safe predecessor-run metadata;
- an accessible operator-console reprocessing panel with stable mutation retry,
  request outcome feedback and Storybook coverage;
- ADR 0007, an updated persistence diagram and a repeatable local verification
  runbook.

## Deliberately Excluded

- document replacement, retention/deletion and malware scanning;
- a production identity provider, user directory or fine-grained authorization;
- automatic failure notifications and escalation workflows;
- S3-compatible storage and external-provider model execution;
- reprocessing a document in `REVIEW_REQUIRED`, which remains an explicit human
  review workflow rather than a technical recovery shortcut.

The bearer token remains a local development fixture. Reprocessing does not
present the platform as a production recovery or access-control system.

## Compatibility

The `/api/v1` namespace remains stable. The status response and generated
contract add optional predecessor metadata, so consumers that ignore unknown
fields remain compatible. The new write endpoint is opt-in and requires the
existing local bearer-token boundary; existing upload, status and review flows
are unchanged.
