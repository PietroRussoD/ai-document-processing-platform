## Implemented local scope

Run every native PDF operation in disposable, restricted Jobs. Upload inspection
is asynchronous: the API validates and stores bytes without opening the PDF,
then the first embedded-text Job records page count and extracts text. OCR uses
a second fresh Job only when needed. The selected local topology is a dedicated
Kind cluster with Calico, controlled by the trusted Compose worker through a
namespace-scoped identity. A Job handles one document and one operation, as
described in the [integration proposal](../security/pdf-parser-integration-proposal.md).

Jobs receive no database, Temporal, operator or Kubernetes credentials, no
application/host data mounts and no Docker socket. They use private bounded
temporary storage, a read-only root filesystem, non-root execution, restricted
privileges, measured CPU/memory/PID/storage budgets and a hard deadline.
The trusted worker bounds, validates and persists the result, including its
protocol, input digest, page count and text limits. Document contents must
stay out of logs and Temporal history.

## Risks and limits

- `runc` containers share the node kernel. This is per-Job containment, not a
  strong sandbox or kernel isolation; package CVEs remain separate open risks.
- The worker's controller identity increases its authority. The namespace
  admission policy now rejects Job templates outside the parser contract, and
  `ResourceQuota` bounds aggregate resources. Kubernetes cluster administrators
  can still alter or remove the policy and its namespace selector; retain a
  private dedicated runtime without ambient admin credentials. The tested
  controls do not isolate the shared `runc` kernel.
- Exec streaming, credential expiry, worker crashes and orphaned Jobs can
  interrupt processing. Local evidence covers cancellation, bounded retries,
  credential renewal and revocation, restart recovery and TTL cleanup; longer
  outages can exhaust retries and leave the workflow failed for operator
  recovery.
- Asynchronous inspection changes upload error timing and page-count semantics.
  The migration, console behavior and recorded workflow compatibility passed
  local checks; malformed PDFs now fail after the API returns `202`.
- Kubernetes cgroup v2 may kill all processes in a container as one OOM group,
  so a cgroup OOM counter cannot identify whether Tesseract or another task was
  the original victim. Per-process diagnosis requires a runtime/configuration
  that exposes a reliable per-process outcome.
- Job startup, image pulls, concurrency and OCR memory vary. Existing local
  baselines do not establish final budgets or capacity guarantees. The parser
  controller's two-Job semaphore is process-local. The dedicated runtime now
  has a shared namespace `ResourceQuota` sized to two Jobs at current settings;
  keep it aligned with per-Job requests and limits. This resource ceiling does
  not establish throughput or deployment capacity guarantees.
- Kind/Calico and external credential provisioning increase local startup and
  recovery complexity. If future topology changes break network denial, narrow
  credentials or cleanup, stop using that topology until the controls are
  restored; retain the documented local-only boundary.

## Follow-ups outside the local release gate

The v1.3.0 target is the documented local Compose + Kind/Calico portfolio demo;
its startup, network boundary, parser paths, failure handling and cleanup have
live evidence. No remote deployment target is defined in this repository.

- Keep the current per-Job limits provisional. Local tests cover synthetic
  photo-style scans, pathological high-entropy input and concurrent 50-page
  workloads, but they do not establish capacity for a broader document corpus.
  A future deployment must validate image pulls and resource behavior against
  its chosen registry/runtime before making capacity claims.
- Permanent node loss and multi-node recovery are outside the single-node local
  target. Add those checks if a concrete deployment target requires them.
- The selected cgroup v2 configuration reports group OOM; retain container-level
  OOM classification and do not claim attribution to a specific child process.

## Excluded

Public hosting, confidential or untrusted-document approval, image distribution,
login/accounts, multi-user or tenant support, antivirus and stronger runtimes
such as gVisor are outside this milestone. Any change to that scope requires a
concrete need and a separate threat/risk decision. The v1.2.0 local,
synthetic-document boundary continues to apply to this v1.3.0 build.
