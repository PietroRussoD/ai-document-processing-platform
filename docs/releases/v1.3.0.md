# v1.3.0 - PDF Parser Containment

Status: development opened on 2026-10-18; parser controller integrated into the
worker's embedded-text and OCR activities. Upload inspection and full Compose /
Temporal runtime lifecycle remain open. The latest released version is
[v1.2.0](v1.2.0.md).

Python metadata and build metrics use `1.3.0.dev0`. The operator console and
OpenAPI contract use `1.3.0-dev.0`. OpenAPI converts the Python development
suffix at the HTTP boundary; the package version remains the source of truth.

## Proposed scope

Move all three native PDF entry points behind disposable, restricted Jobs:
upload inspection, embedded-text extraction, and rasterization/OCR. The
selected local prototype is a dedicated Kind cluster with Calico, controlled
by the trusted Compose worker through a namespace-scoped identity. A Job handles one
document and one operation; OCR may use a second fresh Job for that document,
as described in the [integration proposal](../security/pdf-parser-integration-proposal.md).

Jobs receive no database, Temporal, operator or Kubernetes credentials, no
application/host data mounts and no Docker socket. They use private bounded
temporary storage, a read-only root filesystem, non-root execution, restricted
privileges, measured CPU/memory/PID/storage budgets and a hard deadline.
The trusted worker bounds, validates and persists the result, including its
protocol, input digest, page count and text limits. Document contents must
stay out of logs and Temporal history.

## Acceptance gates

1. **Local topology network gate passed on 2026-10-18.** In a fresh Kind
   v1.37.0/Calico 3.33.0 cluster, a restricted parser probe first reached
   IPv4 Internet TLS, DNS and synthetic application services. Default-deny
   ingress/egress then blocked those tested routes. A worker-shaped container
   on the Compose network reached the loopback-published Kind API using
   `host.docker.internal`, verified TLS and a namespace-scoped token. The
   parser Pod had no IPv6 route, so IPv6 is not covered. The application Job
   controller has since passed a synthetic embedded-text and OCR run against
   its restricted Job manifest and namespace policy; DNS and IPv4 Internet TLS
   worked before default deny and failed afterward. This check ran from the
   host, not from the Compose worker.
2. Standalone probes cover scoped controller permissions, binary/result
   transfer, credential renewal/revocation and cleanup. A worker-shaped
   container confirmed the selected API connection and denial of Secret and
   cross-namespace access. The application controller also created and cleaned
   up real parser Jobs using a namespace-scoped token. Actual worker credential
   delivery/renewal and Temporal-driven cancellation remain to be integrated
   and verified. The worker now requires the runtime settings at startup,
   checks API access and mounts its CA/token directory read-only. The Compose
   worker and Temporal lifecycle have not yet run against Kind. Never mount
   the Docker socket in API or worker.
3. Remove native PDF opens from both API and worker for all three paths.
   Upload byte/media checks remain synchronous; structure and page validation
   may fail asynchronously after `202`. Migrate page count to nullable while
   pending, preserve existing counts and make failures/pending values clear
   in API and console. No silent fallback to parsing in trusted processes.
4. Measure per-Job budgets and enforce concurrency and cleanup after success,
   failure and controller loss. Validate output before any persistence.
   Test malformed input, timeout, child-process and container OOM, crash,
   output overflow and runtime unavailability with synthetic fixtures.
5. Preserve Temporal history compatibility and small activity results. Verify
   replay/resumption of existing workflows and worker restart during a Job,
   including after result persistence but before activity completion. Bound
   transient retries, prevent repeated deterministic failures, avoid duplicate
   persisted outcomes and confirm cancellation cleanup or deadline/TTL fallback.
6. Document and verify the Compose startup path: dedicated cluster creation,
   image loading, network policy, scoped credential provisioning and renewal
   before worker readiness; explicit failure when the runtime is unavailable;
   shutdown and cleanup without touching other clusters or existing data.
   Document the extra prerequisites and recovery steps alongside Compose.

## Risks and limits

- `runc` containers share the node kernel. This is per-Job containment, not a
  strong sandbox or kernel isolation; package CVEs remain separate open risks.
- The worker's controller identity increases its authority. Namespace RBAC
  alone does not enforce safe Job templates; validate the admission boundary
  and retain a private dedicated runtime without ambient admin credentials.
- Exec streaming, credential expiry, worker crashes and orphaned Jobs can
  interrupt processing; deadlines, TTL and idempotent persistence need failure
  evidence. Existing OCR retries can repeat expensive deterministic failures.
- Asynchronous inspection changes upload error timing and page-count semantics.
  Schema migration, console behavior and Temporal compatibility require care.
- Job startup, image pulls, concurrency and OCR memory vary. Existing local
  baselines do not establish final budgets or capacity guarantees.
- Kind/Calico and external credential provisioning increase local startup and
  recovery complexity. Stop integration if network denial, narrow credentials
  or cleanup cannot be reproduced; retain the documented local-only boundary.

## Excluded

Public hosting, confidential or untrusted-document approval, image distribution,
login/accounts, multi-user or tenant support, antivirus and stronger runtimes
such as gVisor are outside this milestone. Any change to that scope requires a
concrete need and a separate threat/risk decision. The v1.2.0 local,
synthetic-document boundary continues to apply during development.
